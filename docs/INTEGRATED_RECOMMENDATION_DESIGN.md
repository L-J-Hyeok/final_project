# 범용 하이브리드 추천 엔진 설계

기준일: 2026-11-13 (Asia/Seoul). [팀 요구사항](TEAM_REQUIREMENTS.md)을 기술적으로 구체화한다. 아래 **확정**은 요구사항, **제안**은 구현 전 협의할 방식이다. 현재 SQL·API 계약을 자동 변경하지 않는다.

## 현재 구현 근거 — 정적 확인

| 현재 코드 | 재사용 역할 / 목표와의 차이 |
|---|---|
| `backend/routes/auth.js`, `auth/middleware.js` | 인증·세션·CSRF 유지 |
| `backend/routes/member.js` | 프로필 버전·소유권·보유 기기 CRUD 유지 |
| `backend/routes/smartphones.js` | 공개 승인·필수 조건·가격 적격 후보 조회. 스마트폰 전용 SQL이므로 그대로 범용 엔진이라 부르지 않음 |
| `backend/services/ai-adapter.js` | 자연어 분석·Gemini·Mock 경계 재사용. 현재 Gemini가 rank 생성; `scoreCandidateForMock`는 테스트용 |
| `backend/services/recommendation-validator.js` | 후보 ID·가격·사양·근거 검증 재사용 |
| `backend/routes/recommendations.js` | 추천 처리·스냅샷·이력. 향후 서버 순위와 AI 설명의 책임 분리 필요 |
| `backend/services/upgrade-advisor.js` | KEEP/교체/보류/추가 질문, 비교 근거. 성능 평가 범위는 제한적 |
| `backend/db/models.js` | 스마트폰 모델·옵션·가격 관측 구조와 기존 ID/FK 보존 |
| `front/src/views/CompareView.vue` | 스마트폰 API 및 태블릿·워치 참고 데이터 비교. 디자인 유지 |

기존 [아키텍처](ARCHITECTURE.md)·[가격 계획](PRICE_COLLECTION_PLAN.md)을 재사용한다. Phase 5 변경의 동작·정확성·완료 여부는 이번에 검증하지 않는다. 현재 수량이나 과거 테스트 통과 수를 설계의 전제로 고정하지 않는다.

## 현재 구현의 한계 — 이전 정적 분석 기준

- Gemini가 추천 제품과 최종 순위를 결정한다. 운영용 로컬 가중치 순위 엔진과 사용자별 가중치 계산은 아직 부족하며 Mock 점수 함수를 운영 엔진으로 간주하지 않는다.
- `upgrade-advisor.js`의 `evaluateUpgradeDecision`은 일부 사양 비교 중심이다. 의미 있는 개선 폭과 교체 비용을 함께 평가하는 기능이 부족하다.
- 전문 벤치마크·성능 측정 자료의 검증·저장 기능은 아직 없다.
- `recommendation-validator.js`의 `validateRecommendationOutput`은 후보·근거 유효성을 검사하지만 순위의 적절성을 로컬에서 재계산하지 않는다.
- 추천 결과에서 비교 화면으로 이어지는 실제 연결은 추가 검증이 필요하다.
- 기존 후보 제한, 프로필 검증, 소유권 확인, 필수 조건 검사, 추천 결과 검증, 업그레이드 분기는 보존한다. 이번 문서 작업에서 코드를 재분석하거나 실행 검증하지 않았으며 후속 변경이 있으면 해당 부분만 재확인한다.

현재 흐름은 `recommendations.js`의 `/analysis` → 분석 초안 검증과, `/recommendations` → `smartphones.js:searchCandidatesForUser` → 선택적 `evaluateUpgradeDecision` → `ai-adapter.js:createAiAdapter().recommend` → `validateRecommendationOutput` → `verifySnapshotFreshness` → 이력 저장으로 구분된다. 목표 파이프라인과 혼동하지 않는다.

## 확정: 책임 경계

목표는 **AI 사용자 의도 분석 + AI 기술 사양 분석 + 검증된 외부 전문 평가 자료 + 로컬 가중치 점수 엔진 + AI 추천 이유 설명**이다. AI의 역할을 설명 생성에만 한정하지 않는다.

AI는 자연어 요구사항에서 구매 목적·예산·필수 조건·선호 조건을 추출하고, 프로필·기존 사용 기기로 개인화하며, 기술 사양의 기능적 의미를 분석한다. 실제 사용 가능한 허용된 검색·조회 기능이 있을 때 전문 자료를 조사하고, 실제 측정 자료를 기반으로 장단점을 분석한다. 서버가 확정한 추천 이유와 제품 비교 결과를 자연어로 해석한다. 측정값이나 출처를 생성하지 않으며 조사 결과는 검증 후 저장·재사용한다.

로컬 엔진은 DB 후보 조회, 예산·필수 조건, 제품 호환성, 검증 자료 선택, 개인 가중치, 정규화, 가성비, 최종 순위, 업그레이드 필요성 판단과 평가의 재현성·일관성을 담당한다. AI가 순위·예산·제품 ID를 바꾸지 못하도록 최종 출력도 검증한다. 공개 DTO에서 내부 점수·가중치를 제외한다.

## 제안: 공통 파이프라인

1. 인증·프로필 버전·선택 기기 소유권 확인. 자연어 분석 초안을 사용자에게 확인받고 현재 명시 조건을 우선한다.
2. 제품군 설정을 선택한다. 미지원 제품군·미완성 설정은 지원 불가 또는 추가 정보로 응답한다.
3. 카테고리 어댑터가 공개 승인된 DB 모델·실재 옵션을 조회한다. 색상×용량을 임의 조합하지 않고 실제 ID를 유지한다.
4. 필수 조건·호환성·가격 적격성으로 후보를 제한한다. 현재 스마트폰 최근 3년 정책은 명시적으로 변경하기 전까지 유지하며 보유 기기 평가는 연식 제한을 적용하지 않는다.
5. 검증된 성능 근거 캐시를 정확한 제품·옵션에 연결한다. 결측은 NULL, 비교 불가능은 별도 상태로 유지한다.
6. 동일 측정 기준 안에서 평가 항목을 정규화하고 사용자 가중치로 로컬 순위를 계산한다.
7. 일반 추천은 적합한 제품 순위를, 업그레이드는 교체 필요성과 이득·손실·비용을 별도로 판단한다.
8. AI에 승인된 제품 ID·서버 순서·검증 근거만 제공해 설명을 생성한다. 불필요한 개인 원문과 내부 점수·가중치는 전송하지 않는 방향을 우선한다.
9. ID·순서·조건·근거·가격 최신성을 재검증하고 스냅샷을 저장한다. 사용자 응답에는 출처·가격 성격·불확실성·자연어 이유를 포함한다.

필요할 때 전문 자료를 조사하는 기능은 현재 추천 요청에서 무제한 웹 검색을 허용한다는 의미가 아니다. 별도 허용된 수집·검증 경로로 반영한다. 이번에는 웹 조사 자체를 수행하지 않는다.

공통 코어와 카테고리별 `spec definitions / eligibility / compatibility / metric normalization / preference weights / evidence policy`를 분리한다. 명칭은 설계 예시이며 새 파일·테이블의 확정 명세가 아니다.

## 제안: 성능 근거와 캐시

근거 레코드는 제품/옵션 및 칩셋 식별, 출처 URL·제공자, 측정 항목·값·단위, 도구/벤치마크 버전, OS·전력·측정 환경, 측정/게시/확인 시각, 검증 상태, 사용 권한과 갱신 상태를 관리한다. 실제 컬럼·테이블은 DB 담당과 협의한다.

AI 추출 → 원문·제품 식별·단위 검증 → 비교 가능 집합 분류 → 승인 → 캐시 반영 순서를 제안한다. 버전·환경이 다른 점수는 바로 혼합하지 않는다. 캐시 키는 옵션·지표·버전·환경·출처를 포함하고 변경 출처·재검증 기한에 따라 필요한 자료만 갱신한다. 미승인·출처 불명·기한 경과 자료는 정책에 따라 제외/재검토하며 자동 승인하지 않는다.

Geekbench·3DMark·Cinebench·Notebookcheck·RTINGS·제조사는 후보일 뿐 사용 허가가 아니다. 이용약관·robots.txt·저장·재배포·AI 이용 권한을 별도로 확인하고 우회 수집하지 않는다. 측정 환경에 따라 실제 성능이 다를 수 있음을 표시한다.

## 제안: 점수·가성비·결측 정책

정규화 기준 집합과 버전을 고정하고 높을수록 좋은 값, 낮을수록 좋은 값, 목표 범위·정성 항목을 구분한다. 예시 내부식은 `합계(사용자 가중치 × 정규화된 검증 항목값)`이며 실제 가중치·임계값·가성비 함수는 미확정이다. 결측을 0으로 치환하거나 근거 적은 제품이 유리해지도록 남은 가중치를 무조건 재분배하지 않는다. 최소 근거 충족도와 비교 가능성을 먼저 검사한다.

가격은 verified_sale / reference_sale / official_launch를 구분한다. 운영의 기존 최신성·배송비·구매 조건 규칙을 보존하고, 개발용 대체 가격을 실제 구매가로 표시하지 않는다. 가격 NULL이면 가격 기반 순위·가성비를 확정하지 않는다. 출시가와 현재가 차이는 양쪽 근거가 적격일 때만 표시한다.

## 확정 목표: 다나와 가격 경계 — 최종 계약 대기

현재 목표는 danawa-cli 단일 최저가 → 정확한 옵션 매칭 → MySQL 참고 가격 저장 → 추천·업그레이드·비교에서 활용이다. 출처, 조회 시각, 유효기간, 변동 이력, 다나와 상품 상세 URL을 유지한다. 판매처별 가격 전체 조회는 향후 TODO이며 현재 완료 기준에 포함하지 않는다.

가격은 후보의 예산 검사, 로컬 가성비 평가, 업그레이드 구매 비용 평가, 저장 직전 최신성 검사에 사용한다. 참고 최저가는 확정 구매 가격이 아니다. 기존 가격 적격·개발용 대체 정책을 자동 완화하지 않으며, reference_sale의 평가 허용 범위·배송비 미확인 처리·필드명·TTL·저장/API 계약은 Antigravity 작업 완료 후 확정한다. 이 문서는 다나와 코드·스키마를 변경하지 않는다.

## 일반 추천·업그레이드·비교의 분리

일반 추천의 질문은 “사용자에게 어떤 제품이 가장 적합한가?”이며 예산·목적·선호·프로필·가성비를 평가한다. 보유 기기 없이도 동작한다. 업그레이드의 질문은 “현재 제품을 교체할 가치가 있는가?”이며 핵심 불편 해결·실제 개선 폭·구매 가격·잃는 기능·교체 긴급성을 평가한다. 공통 평가 엔진을 재사용하되 최종 판단 정책은 분리한다. 업그레이드는 소유권이 확인된 현재 기기와 사용자 만족·불편·교체 이유를 필수 맥락으로 삼는다. 비공개·단종 보유 기기도 검증 가능한 사양은 평가하되 신규 공개 후보로 승격하지 않는다.

KEEP은 현재 필요 충족과 유지 이득, REPLACE는 불편 해결에 관련된 검증 개선과 비용, DEFER는 결론/구매를 미룰 근거, CLARIFY는 필요한 최소 추가 정보로 구분한다. 자료 부족과 개선 없음은 구별한다. 기존 wire status `recommend`를 REPLACE 의미로 사용하는 계약은 유지하며 이름 변경은 별도 계약 검토한다. 후보 개수 제한이 유지 판단을 가로막거나 단일 미측정 항목이 전체 후보를 자동 탈락시키는 문제를 후속 점검한다.

비교는 우세·동률·단순 차이·자료 부족·비교 불가를 지표 정책으로 판정한다. 개인 선호 장단점과 객관적 우세를 구분한다. AI 설명 실패에도 기존 수치 비교는 유지한다. 과거 추천은 당시 스냅샷으로 보존하고 현재 유효성·재평가는 별도 표시한다. 명시적 개인정보 삭제 정책은 유지한다.

## 실패 처리 및 미해결 결정

- 조건 충돌/미입력: 필요한 질문만 반환. 후보 없음: 조건 자동 완화 금지.
- 자료 부족: 결측·비교 불가와 필요한 자료 표시. AI의 추측으로 채우지 않음.
- AI 해석 실패: 구조화 입력으로 전환 제안. 설명 실패: 확정된 로컬 결과와 검증 사실 템플릿 제공을 제안. 재시도·비용 한도 필요.
- AI가 제품·순서·수치 변경: 결과 거부. 갱신된 가격·조건과 충돌: 재검증 후 재요청 안내.
- 추가 예산 후보는 본래 예산 내 순위와 분리하고 사용자 선택 없이 기본 조건을 바꾸지 않음.
